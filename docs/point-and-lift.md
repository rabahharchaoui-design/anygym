# Point & Lift (Rabah, Nov 27 2026: decisions locked 2:24 AM)

Point the camera at a gym machine. AnyGym says what it is, adds it to your gym, shows you how to use it, and fits it into today's workout. It must feel premium, flow smoothly and have zero bugs. Starts after M17, G1, G1b and the open audit majors (pwa 2, honesty 1, run 1) are done. Built in phases PL-a to PL-g, one or more commits each; a phase is ticked only when its tests pass on gmini and CI is green, and each phase is reported with its commit hash.

Art and motion are from Grok and Pluto at ~/anygym-art-drop/point-and-lift/ on gmini. Read its README.md and manifest.json before any phase and follow Pluto's timings exactly: the tab icon, the lock on, the result card, the muscle map SVGs and the setup diagrams all come from it. The pass is committed into the repo like the badge art: what ships (tab icon SVGs, the small muscle maps and muscle-map.css, machine glyphs, how to schematics, empty state) under public/scan/, the README, manifest and previews under docs/art/point-and-lift/. Screens 01 to 10 are the layout reference (393 x 852 pt): viewfinder 313 x 400 pt at (40, 150), 34 pt bracket arms with a 4 pt stroke, the graphite hint panel from y 592 to 766 with the 64 pt shutter, the card rising to y 408. The geometric muscle maps are for the scan card only; the app's main muscle map stays as it is (Pluto's note: using them app wide is Rabah's call). Pluto's open points are handled here: the SPEC 0.5 privacy line is updated (Rabah's decision), five tabs (option C), and the low light brackets are white dashed if titanium dashed tests hard to see on a real dim feed.

## Rules that apply to every phase
- Flat Monolith: graphite #131417, white, titanium #8A9099, ice blue #9FD3FF the only accent, square cuts, no glass, no gradients.
- Motion only from src/ui/motion.ts: 220 ms cubic-bezier(0.2,0,0,1) pushes, 160 ms fades, press scale 0.97. Lock on and card timings exactly as in Pluto's README. Reduce Motion: crossfades only, haptics kept.
- Reuse, never copy: the equipment picker (src/screens/intake/Steps EquipmentStep), the gym data and saves (src/db/gymList.ts setGymEquipment), the G1 check and `equipmentCheckedAt`, the exercise catalog (data/catalog.json, src/lib/catalog.ts), cues (data/exercise-cues.json, src/lib/exerciseInfo.ts), demos (data/catalog-demos.json), swaps (src/lib/swap.ts and src/lib/gymSwitch.ts), Sheet, Button, Toast. No second copy of a button, card, sheet or helper.
- No bad data: never state a guess as fact, never show a demo, muscle, cue or starting weight the app is not sure of. Cues and the common mistake come from the catalog sources, never invented; a machine without a source cue shows the step it does have and nothing more.
- Privacy (locked): recognition runs in the cloud through our own backend. Before upload the photo is downscaled and cropped to the machine. Photos are never stored or logged, on the phone or the server. The first time, the app asks for the camera with one line saying photos aren't kept. No secret, key or personal name in the client bundle (the existing name and secret scans cover it).
- 60 fps on the viewfinder and transitions (transform and opacity only). The camera stream stops when you leave the tab, when the app goes to the background (visibilitychange and pagehide) and when a sheet covers the viewfinder: no battery drain, no camera light left on.

## The machine catalog (PL-a)
- data/machines.json, about 60 entries to start: common commercial machines (leg press, hack squat, leg extension, leg curl seated and lying, chest press, pec deck, rear delt fly, lat pulldown, seated row, assisted pull up and dip, shoulder press, cable crossover, functional trainer, smith machine, calf raise standing and seated, hip adductor and abductor, glute kickback, hip thrust machine, back extension, ab crunch, preacher curl, T bar row, belt squat, pendulum squat, chest supported row and more), hotel gym stations (cable tower, adjustable bench, dumbbell rack, multi gym), cardio (treadmill, bike, rower, elliptical, stair climber) and free weight stations (power rack, flat bench, dip station, pull up bar).
- Each entry: `id`, `name`, `aliases` (what people and signs call it), `muscles` (primary and secondary, the same muscle ids the app's muscle map uses), `setup` (seat, pad, grip, start and end, only from a source), `mistake` (one, only from a source), `equipment` (the EquipmentId it maps to), `exercises` (catalog exercise ids it covers, each one real in data/catalog.json), `startWeight` rule (see How do I use it).
- Equipment profile keys: every entry maps to an EquipmentId. Machines the app has no id for yet (hack squat, glute kickback, hip thrust machine, ab crunch, preacher curl bench, T bar row, belt squat, pendulum squat, assisted pull up, rear delt fly, standing calf raise, chest supported row) get NEW ids appended at the END of EQUIPMENT_IDS (the PLAN 3.5j rule: saved lists keep their order) and appear in the equipment picker's matching group. A machine whose exercises are not in the exercise catalog yet is left out of the first catalog rather than shown with nothing to do.
- Unit tests: every entry is complete, every exercise id exists, every equipment key is a real EquipmentId, ids and aliases are unique, lookup by alias works case insensitively.

## Recognition (PL-a)
- One interface, `recognize(frame): Promise<Recognition>`, in src/lib/pointLift/ (client) so an on device model can replace the server later without touching the screens. `Recognition` = `{ status: 'ok', guesses: { id, confidence }[] } | { status: 'offline' | 'timeout' | 'limited' | 'error' }`.
- Server: a new POST /v1/recognize route on the existing anygym-api worker (workers/anygym-api), reusing its origin check, body limits and rate limiting (src/limits.ts). The API key or binding lives only in the worker.
- The model gets the cropped frame and the catalog's ids and aliases, and must answer JSON only: up to 3 `{ id, confidence }` with ids from the catalog, plus `box` for the top guess (x, y, w, h as fractions of the crop) so the brackets can lock onto the machine; no box means the brackets lock onto the viewfinder. The worker validates the answer: unknown ids are dropped, confidences clamped to 0..1, anything else counts as no guess.
- Provider: a cloud vision model called only by the worker, which holds the vision API key as a Cloudflare secret; the client never sees it. Default model: Claude Haiku vision (about $0.002 a scan with the catalog prompt cached); Rabah adds the key as a worker secret, Claude never types it. Accuracy is measured on a labelled set of real photos from Rabah's gyms (at least 3 per machine for the 20 most common); the right machine must be in the top 3 at least 90% of the time.
- Before upload (client): crop to the lock on frame (the user aims the machine inside it), downscale to 512 px on the long side, JPEG about 0.7 quality, strip metadata. Sent in memory, never written to storage.
- Server: never stores the photo or logs it; logs only the guessed ids, confidences and timing. Rate limit per user the way reports already do it (takeRate on the salted IP hash in workers/anygym-api), plus a random anonymous scan id the app makes once and keeps on the phone (no personal data), whichever is hit first: 30 scans per hour, 200 per day; over it returns `limited` and the app shows the list fallback.
- 5 s timeout from shutter to answer. Offline, timeout, limited and error all show a clear one line message plus "Pick from list".
- Confidence (in one place, unit tested; Pluto's rule, README section 3), shown as 3 pip bars plus one word, never a percentage: Sure (3 pips) when the top guess is 0.85 or more and at least 0.25 ahead of the next: the single result card. Likely (2 pips) from 0.60 to 0.85: the single card, labelled Likely, with "Not it?" kept visible (it opens the other guesses). Maybe (1 pip) below 0.60, or the top two within 0.15: the Not sure card with the top 2 or 3 guesses and "None of these", no muscle map and no setup until the user picks. No guess at 0.15 or more: "Not sure what this is" plus Pick from list. The thresholds are placeholders until the model is measured (PL-a), then set from the measurement. The word is also the accessibility label ("Match: Sure").
- Mocked tests: the client against a fake server (each status, malformed JSON, unknown ids, slow answers), the worker route against a fake model (validation, limits, no photo in any log or store).

## The tab, viewfinder and fallbacks (PL-b)
- The Scan tab is built together with the M19b Monolith tab bar (one icon family, the label in 12 to 13 pt, active white with the ice blue bar, inactive titanium, every target at least 44 pt, home bar safe area). The M19b tab bar parts are pulled forward into PL-b; the rest of M19b stays where it is.
- Tabs (locked): five tabs, Today, Plan, Scan, Run, You, with Scan in the centre. The tab label is "Scan", the screen header "Point & Lift", the icon from the art pack. History moves into You with no feature lost: every History screen, filter and detail is reachable from You, old /history links and deep links land on the same screens, and Back returns where it should. Tests cover the old links, the back stack and every History feature from its new place.
- Opening the tab goes straight to the rear camera viewfinder, full bleed, with the lock on frame and a shutter. First time: a clean explainer with one line, "AnyGym only uses the camera to recognise machines. Photos aren't kept.", and "Turn on camera". Denied, unavailable or no camera: a short line and "Pick from list" (the existing equipment picker in a sheet), never a dead end. iOS Home Screen web app camera access is tested on a real iPhone before PL-b is ticked.
- Search: the brackets breathe (6 pt in and out, opacity 1 to 0.72, 1400 ms alternate, sine in out) and the hint fades in once (160 ms). Auto detect: the app compares tiny downscaled frames on the phone; when the picture holds steady for about 0.6 s it captures by itself; tapping the shutter captures at once. No steady frame after 4 s: the hint crossfades to "Can't tell yet" and the shutter turns white (manual). Low light (from frame brightness): darker feed, dashed brackets, "Too dark to see it", and the torch button only when the camera track reports a torch.
- Capture: breathing stops and holds, the frame freezes, the hint says it is looking, and the crop uploads.
- Lock on, exactly Pluto's storyboard (README section 4, every step table), with t = 0 when the answer arrives: brackets push from the viewfinder to the machine box (220 ms cubic-bezier(0.2,0,0,1)) and turn white to ice (160 ms linear); at 220 ms they land, the haptic tick fires and the hint reads "Got it"; the sweep line runs 220 to 540 ms then fades (160 ms); the feed dims to 45% (220 to 380 ms); the card rises 380 to 600 ms, its content fades in from 460 ms with an 8 pt rise, the pips fill at 520, 560 and 600 ms; taps are accepted at 600 ms; all settled at 760 ms. Below Likely before 380 ms: the brackets fade back to white and breathing resumes, and the Not sure card follows. Reduce Motion: no breathing, push, sweep or rise; the brackets jump to the box and crossfade to ice (160 ms), the card crossfades in at rest (160 to 320 ms), the tick kept.
- Timing (Rabah, Nov 27 2:40 AM): Pluto's timings exactly, no changes. The 300 ms rule is measured as lag: the answer is on screen within one frame (the brackets start their push at once, the hint reads "Got it" by 220 ms), nothing waits on work after the answer (the card's content is rendered before the answer is shown), and the card rises at Pluto's 380 ms. Tests mock the recognizer with a realistic 600 ms delay and measure this.
- Haptics through src/ui/haptics.ts, the app's one haptics helper (light tick on lock, a firmer one on Added, following the existing haptics setting); where the phone has no haptics the visual lock stands alone, never a fake.
- The camera stops on leaving the tab, on backgrounding and under any sheet, and starts again on return.

## The result card (PL-c)
- Slides up over the paused viewfinder: the machine name large, the main muscles on a small muscle map (Pluto's SVGs; placeholder: the app's existing map), and the confidence as 3 pip bars plus Sure, Likely or Maybe. The card shows within 300 ms of the response.
- Guesses state: the 2 or 3 choices as large tappable rows, then "None of these" (opens Pick from list). Tapping a choice makes it the answer. Never a guess stated as fact.
- Three actions: Add to <active gym>, How do I use it, Do it now. "Scan again" returns to the live viewfinder.

## Add to gym (PL-d)
- One tap adds the machine's equipment key to the active gym through setGymEquipment (the same code as the G1 check and the picker). Already there: the button reads "In <gym>" and does nothing.
- Added follows Pluto's storyboard frames 07 and 08: on tap the text turns ice and the bar grows 4 to 8 pt, the label crossfades (160 ms) to a check that draws in 220 ms and "Added to <gym>", a tick when the check lands, Undo for 4 s. Scanning several in a row stays in camera mode with a running count ("3 added").
- Adding scans counts toward confirming that gym: the first scan add at a gym that is not confirmed sets `equipmentCheckedAt`, because the person just confirmed real equipment there (the G1 rule). Tests: the gym record after an add equals what the picker would save for the same tap.

## How do I use it (PL-e)
- A setup card (Pluto's screen 10): the looping schematic (2400 ms: push 0 to 900 ms cubic-bezier(0.4,0,0.2,1), hold 300, return 900, hold 300; Reduce Motion shows the start pose with the end pose ghosted at 22%), then Seat, Grip, Start and Common mistake rows (the mistake label in ice, never red), and Do it now. Only machines with a schematic show one; the others show the reviewed catalog demo frames, else no diagram, never a wrong one.
- Starting weight: from the user's history on the same exercise at any gym (the progression engine's next weight); with no history, a conservative default from the catalog rule (for example the lightest stack plate or the empty sled), labelled "Start light". Shown in the gym's unit. Never a number the app is not sure of.

## Do it now (PL-f)
- If today's plan has an exercise this machine can cover, offer the swap ("Swap Barbell row for Seated row?") using src/lib/swap.ts, the same logic as the switch preview, with sets and reps adjusted by the same rules. Otherwise add the machine's exercise to the current workout, or start a new one with it.
- Mid workout: after Do it now, return to the workout screen with that exercise open and its first set ready to log.
